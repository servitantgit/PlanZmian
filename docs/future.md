## 1. Що свідомо залишаємо як є

- Один інстанс = один завод / одна «правда» графіка для всіх користувачів цього інстансу.
- Особисті дані (відпустки, OT, нотатки, Drive) — локально-first, не в публічному D1.
- Немає self-service SAAS, білінгу, конструктора довільних циклів змін (2/2/4 тощо) у поточному scope.

Масштабування «просто деплой копії на інший CF project» **вже можливе** без змін коду (окремі D1 + secrets + seed). Нижче — інша модель, якщо колись знадобиться **один** хостинг на багато компаній.

## 2. Цільова ідея: tenant на піддомені

### 2.1 Сенс

| Замість | Стає |
|--------|------|
| Новий Cloudflare Pages project на кожну компанію | Один Pages project |
| Окремий репозиторій / форк | Той самий `main` |
| Жорсткий `schedule_id = 'gillette'` | Tenant з **hostname** |

Приклади URL:

```text
gillette.planzmian.pages.dev     → tenant/schedule_id = gillette
acme.planzmian.pages.dev         → tenant/schedule_id = acme
```

Прод-домен пізніше краще свій: `*.planzmian.app` (wildcard DNS + CF custom domains), не лише `*.pages.dev`.

### 2.2 Хто що робить

- **Звичайний користувач** відкриває піддомен своєї компанії → бачить лише її factory-графік з D1 + свої особисті дані в браузері/Drive.
- **Адмін компанії** (email у списку адмінів *цього* tenant) малює й **Publish** у свій `schedule_id`.
- **Платформний онбординг** (коли з’явиться потреба): створити tenant + першого адміна + порожній/seed рік — скрипт або закрита internal-адмінка, не публічна реєстрація.

### 2.3 Чому не query `?tenant=`

`schedule_id` / tenant **ніколи** не брати з body/query клієнта як джерело істини. Тільки:

1. `Host` / subdomain, або  
2. внутрішній мапінг після автентифікованого platform-admin.

Інакше можливий cross-tenant read/write.

## 3. Дані (ескіз)

Поточні таблиці вже близькі: `schedule_years` / `schedule_history` з `schedule_id`.

Можливе розширення (коли робитимуть):

```text
tenants
  id            TEXT PRIMARY KEY   -- = subdomain / schedule_id
  name          TEXT NOT NULL
  created_at    TEXT NOT NULL

tenant_admins
  tenant_id     TEXT NOT NULL
  email         TEXT NOT NULL      -- lowercase
  PRIMARY KEY (tenant_id, email)
```

На старті можна обійтись без `tenants`: subdomain ∈ allowlist або рядок існує в `schedule_years`. Адміни — або таблиця, або структурований secret (гірше для росту).

**Правило запису:** PUT завжди `(schedule_id з host) + year`; email після Google `tokeninfo` ∈ `tenant_admins` для цього `schedule_id`.

## 4. Зміни в коді (коли дійде черга) — checklist

Порядок milestone’ів, не «все одразу»:

1. **Host → schedule_id** у `GET /api/schedule` і `PUT /api/admin/schedule/:year` (заглушка: лише відомі id, інакше 404).
2. Прибрати / параметризувати захардкожений `'gillette'` у `functions/*`, `js/schedules/remote.js` (клієнт може лишитись «сліпим» — tenant задає сервер по Host).
3. **Auth per tenant** — не глобальний плоский `ADMIN_EMAILS` на всі графіки.
4. Google OAuth: authorized origins для кожного піддомену (або політика Google під wildcard, якщо доступна на момент реалізації).
5. Drive appData: префікс `tenantId` у імені файлу бекапу, щоб один Google-акаунт на двох піддоменах не змішував дані.
6. Онбординг tenant (скрипт / internal tool).
7. Wildcard DNS + сертифікати.

Phase 3 (history / rollback) лишається **per schedule_id** і добре комбінується з tenant.

PWA: кожен піддомен = окремий install (зазвичай бажано).

## 5. Альтернатива, яку не забувати

**Окремий CF project + D1 на компанію** — без multi-tenant у коді.

| | Піддомени + рядки в D1 | Окремий Pages на компанію |
|--|------------------------|---------------------------|
| Ізоляція | логічна | сильніша |
| Оновлення продукту | один деплой | N деплоїв |
| Нова компанія | DNS + рядок + адмін | новий project + secrets + migrate |
| Складність коду | вища | нижча |

Поки клієнтів мало і немає спільної платформи — **копія деплою** часто достатня. Ідея §2 має сенс, коли важливий **один** реліз на всіх і self-service / багато tenant’ів на одній інфраструктурі.

## 6. Інші ідеї (backlog продукту, не tenant)

Не зобов’язання; лише щоб не загубити контекст обговорень:

- Phase 3: історія ревізій + Rollback UI.
- Експорт годин / OT / відпусток (CSV) для майстра чи офісу.
- Спільні нотатки дня / легкий handoff між змінами.
- Запити на підміну зі зміною factory-клітинки після підтвердження.
- Нагадування про зміну / ліміт відпусток (PWA notifications обережно).

Окремий продукт (не Plan Zmian «для однієї компанії»): універсальний конструктор циклів змін, калькулятор зарплатних надбавок під кодекс, журнал зміни як окремий застосунок — лише за окремим рішенням.

## 7. Критерій «починаємо tenant»

Реалізацію §2–4 починати **лише якщо** є хоча б одне з:

- друга компанія на **тому ж** хостингу з окремим адміном і графіком;
- явна відмова підтримувати N окремих CF project;
- готове ТЗ (auth, DNS, onboarding, Drive-імена) і час на тест cross-tenant ізоляції.

До того — цей файл лише якір ідеї в репо.
